# Australian Information Security Manual (ISM) mapping

The Australian Signals Directorate's Information Security Manual (ISM) is
organised as guidelines containing numbered controls (ISM-NNNN). The
"Guidelines for Software Development" cover application development
practices; other guidelines cover supply chain and system management. This
document maps PRISM's evidence to the controls a software supplier would
most likely use it for, in two directions:

1. **PRISM as a tool** a developer uses to meet a control for *their*
   software.
2. **PRISM as software** that is itself assessed (its own supply chain and
   development).

**Read this first.** No IRAP assessor has reviewed PRISM or this mapping.
The ISM is revised several times a year and controls are added, reworded
and withdrawn; the identifiers and the paraphrased control topics below are
given for orientation and **must be checked against the ISM release you are
assessed against** (the ISM text is not in this repository). A tool can
contribute evidence toward a control; it cannot by itself implement an
organisational control. Evidence identifiers are defined in
[EVIDENCE.md](EVIDENCE.md).

## 1. PRISM as a tool for the developer's software

| control (identifier to confirm) | topic (paraphrased) | status | PRISM's contribution | not addressed |
|---|---|---|---|---|
| ISM-0401 | secure-by-design principles and secure programming practices are used in application development | Partial | Detects and, for its encoded properties, proves the absence of classes of insecure coding defects: signed overflow (CWE-190), division by zero (CWE-369), shift UB, out-of-bounds array access in the `bmc` stage (CWE-125/787), plus lint classes mapped to CWEs in `src/prism/taxonomy.cpp` / `prism/taxonomy.py` (E17). | The practices themselves, training and design review. |
| ISM-0402 | applications are tested for security vulnerabilities (static and dynamic application security testing) before initial and subsequent releases | Partial | Static analysis (lints, cppcheck, clang-tidy, Semgrep, CodeQL, Infer when installed), formal analysis (`bmc`, `pir`), and dynamic testing (sanitizer runs, AFL++, libFuzzer, KLEE when installed and allowed with `--allow-exec`) in one run, with a SARIF report for review (`docs/USER_GUIDE.md#4-sarif`). Tests that did not run are listed as `NOTRUN`, never passed (Law 1, E17). | Testing by an independent party; web/application-level DAST; penetration testing. |
| ISM-1780 | SecDevOps practices are used for application development | Partial | A CI gate: `--fail-on defect` / `--fail-on gap` exit codes and SARIF upload to code scanning (`docs/USER_GUIDE.md#8-ci-integration`, `docs/USER_GUIDE.md#5-exit-codes-and---fail-on`). | The rest of the practice (pipeline security, deployment, monitoring). |
| ISM-1238 | threat modelling is used in support of application development | Not addressed | | PRISM does not model threats. |
| ISM-0400, ISM-1419, ISM-1420, ISM-1422 | segregation of development, test and production environments; development only in development environments; production data kept out of test; unauthorised access to the authoritative source prevented | Not addressed | PRISM reads a checkout and, without `--allow-exec`, executes nothing from it (E16), which keeps it usable inside a segregated development environment. | Environment segregation and access control are organisational. |

|---|---|---|---|---|
