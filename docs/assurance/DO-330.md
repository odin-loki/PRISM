# DO-330 tool qualification considerations for PRISM

RTCA DO-330 (Software Tool Qualification Considerations) is used with
DO-178C when a tool eliminates, reduces or automates a software life-cycle
process without its output being verified. This document works out which
Tool Qualification Level (TQL) PRISM would need, lists the qualification
data DO-330 expects, and says for each item what exists in this repository.

**PRISM is not qualified at any TQL.** Qualification is granted per
project, by the applicant, with the certification authority's agreement; no
such project exists. Nothing here is qualification data in the DO-330
sense. It is a gap analysis. Section numbers and table references are as
commonly cited; check them against the licensed RTCA text.

## 1. Tool classification and TQL

DO-178C section 12.2.2 classifies a tool by the worst effect of an error in
it:

| criterion | meaning | does it apply to PRISM? |
|---|---|---|
| 1 | tool output is part of the airborne software and could insert an error | **No.** PRISM writes reports; it does not generate or transform airborne code. (The AI `repair` stage reports candidate patches in the report; it does not edit the checked tree, and applying a patch is a human action whose result must be verified again: E18.) |
| 2 | a tool that automates verification and whose output is used to justify the elimination or reduction of other verification or development processes | **Yes, if** a `PROVED*` verdict is used to reduce reviews or testing (for example robustness testing for overflow or division by zero). |
| 3 | a tool that, within its intended use, could fail to detect an error | **Yes** in every other use of PRISM as a verification tool. |

TQL from DO-178C Table 12-1 as commonly cited:

| software level | criterion 2 | criterion 3 |
|---|---|---|
| A | TQL-4 | TQL-5 |
| B | TQL-4 | TQL-5 |
| C | TQL-5 | TQL-5 |
| D | TQL-5 | TQL-5 |

So the most demanding realistic target is **TQL-4** (criterion 2 at level A
or B). TQL-1 to TQL-3 would only apply if PRISM's output became part of the
airborne software, which it is not designed to do.

## 2. The qualification-relevant part of PRISM

Only the path to a verdict that reduces verification needs qualifying.
Everything else can be quarantined, which is the design of the verdict
module and the trusted base:

- The **verdict audit** runs on every report and only lets the stages
  `optional`, `esbmc`, `dafny`, `contracts`, `wp`, `bmc`, `pir`, `harness`,
  `review` and `ltl` keep a formal verdict (`thm:proving_stages`,
  `thm:audit_nonproving`, E04). Fuzzers, lints and model output can never
  produce a proof (`thm:no_path_fuzzer_or_model_to_proof`). A qualification
  could therefore be limited to the proving stages actually used, and to
  one of them, for example `pir`.
- What a proof depends on is listed in `docs/TRUSTED_BASE.md` (E07).
- External provers (ESBMC, CBMC, Dafny) are separate tools with their own
  qualification status; PRISM only reports their verdicts.

## 4. What PRISM already offers a qualification effort

- **A small, proved verdict module.** The verdict laws are proved in Lean
  for the model (E02: `thm:proved_bounded_never_merge`,
  `thm:notrun_never_clean`, `thm:admit_certified_iff`, `thm:audit_certified`)
  and the C++ and Python verdict code is checked entry by entry against the
  model's truth tables (E03). This is the part of the tool that decides
  which word is printed.
- **Design-level soundness proofs** for the PIR encoder, UB
  instrumentation, k-induction, Houdini, contracts and a bit-blaster (E05,
  E06), with the gap to the C++ code written down.
- **A measured, gating conformance suite** with known answers, including a
  pinned SV-COMP subset and NIST Juliet (E09), and random-program testing
  (E10).
- **An honest-failure design.** Missing tools and unencoded constructs are
  reported, never passed (Laws 1, 7; E17).
- **A trusted-base statement** (E07) that names every component a proof
  depends on.

## 5. What is missing before a TQL-4 qualification is plausible

1. The proving stage to be qualified (`pir` is the candidate: clang front
   end, translation validation) must be proved or verified against its
   specification, or its output must be independently checked. Certified
   mode (`--certified`, E08) checks the solver's answers: the `pir` stage
   emits `PROVED-CERTIFIED` when every VC has a checked LRAT certificate,
   and on the Lean-proved bit-blaster path the CNF itself comes from proved
   code. The C++ encoder, memory model and clang stay trusted (E07), and
   `BOUNDED`, `PROVED-UNBOUNDED` and plain `PROVED` still trust Z3.
2. TQP, TOR, TR, TCI, TAS and QA records written for a specific project.
3. Traceability from TOR items to conformance tasks and tests.
4. Independent review of the above.
5. Resolution of the open robustness findings in `docs/FUZZ_SELF.md` and of
   the soundness items in `docs/CONFORMANCE.md#known-issues`.
6. A `--version` output and a recorded command line in every report, so
   that a result can be tied to a configuration item.
