# Review of OS-PROVING-FEEDBACK.md against this repository

Reviewed repository: `C:\ParanoidBSD\PRISM` (shallow clone of odin-loki/PRISM). Reviewer rule: read only, nothing built, nothing
run. Every claim below comes from reading source or docs; where a statement could only be settled by running PRISM it
is marked UNVERIFIED. Paths are relative to the repository root. "OS-Proving data" figures (24,806 functions, 3,501,
6,820, 118 s and so on) belong to the other project and were not checked here (UNVERIFIED).

Legend: CONFIRMED = PRISM really lacks it or behaves that way. ALREADY-DONE = PRISM does it. PARTLY = something exists,
something is missing. WRONG = the claim about PRISM is incorrect.

## 0. Two facts that change how the whole draft reads

1. **`prism prove` is not a C-function prover.** In this repository `prism prove FILE.lean THEOREM` is the Lean proof
   search driven by a prover LLM (`src/prism/cli.cpp:312`, `docs/AI.md:221-290`; model calls, `lake env lean`, kernel
   check, axiom audit). The C-code engines are stages of the one command `prism PATH`: `contracts`, `wp`, `bmc`, `pir`,
   `harness`, `review` (`include/prism/pipeline.hpp:16-20`). The draft (section A and item 5) speaks of "one `prism prove`
   took about 118 s", "grammar mask was 95% of decode time" and "a pure deterministic path that never touches an LLM".
   Grammar masking is the FORGE sampler used by the LLM features (`docs/AI.md:127-160`). The deterministic stages
   (`--no-llm`, and Law 4) never call a model. What command OS-Proving actually timed is UNVERIFIED; the draft must say which
   command and which stages, because the remedy differs (LLM decode speed vs Z3/clang time).
2. **PRISM is not the engine the draft implies for kernel code.** The pir stage (the one that proves) works on LLVM IR
   from `clang -O0` and says `UNENCODED` (so `NEEDS-HARNESS`) for external calls without a model, volatile/atomic loads
   and stores, integers wider than 64 bits, inline asm without a contract, vectors and more (`docs/PIR.md:177-198`).
   Kernel idioms (`READ_ONCE`, `spin_lock`, `kmalloc`, `copy_from_user`) fall in these classes. No kernel model exists:
   grep for `kmalloc`, `spin_lock`, `copy_from_user` finds only lint/syntax tables, not pir models
   (`src/prism/astlint_checks.cpp`, `src/prism/syntax_gates.cpp`). The draft is right that coverage on kernel code is
   thin, but several of its remedies already exist in generic form (see the table).

## 2. Important things the draft missed

- **Verdict vocabulary and laws.** Eighteen verdicts in a fixed lattice, `PROVED-CERTIFIED` > `PROVED-UNBOUNDED` > `PROVED` >
  `PROVED-ASSUMING` > `BOUNDED` (`docs/VERDICTS.md`). The draft's proposed new verdicts (`PROVED-C-SEMANTICS`,
  `VACUOUS`, `WEAK`, `ENGINE-DISAGREE`, `OUT-OF-MEMORY`, `ENGINE-ERROR`) would each need a Lean change plus regenerated tables.
  Nine laws are enforced; the verdict audit demotes an inadmissible claim after every stage (`docs/VERDICTS.md`
  "The verdict audit"): only the origins `solver` and `external-prover` may prove; fuzzers, models, lints and
  execution stages never can.
- **Proof levels PRISM already reports.** `PROVED-ASSUMING` (explicit requires/harness), `BOUNDED` (bound k), `PROVED`
  (loops close), `PROVED-UNBOUNDED` (k-induction or invariants), `PROVED-CERTIFIED` (LRAT checked). Strict conformance
  headline: 0 wrong proofs; pir 302/379 true tasks proved, 165/364 false tasks refuted with a replayed counterexample
  (`docs/ROADMAP_STATUS.md:12-22`).
- **Certified mode and a small trusted base.** `docs/TRUSTED_BASE.md` lists exactly what a `PROVED-CERTIFIED` trusts.
  Lean-proved bit-blaster and LRAT checker (`proofs/techniques`), cake_lpr, nanoda re-check of every Lean project.
- **Refinement proofs.** `proofs/refinement` (core Lean 4, no Mathlib) proves the LLVM-to-PIR translator correct for a
  fragment, with per-run checking that the C++ translator's output equals the proved translator's output
  (`docs/PROOFS_REFINEMENT.md:40-55`), a formal memory model `proofs/semantics`, and the verdict lattice
  `proofs/Prism/Verdict.lean`. This is the main thing that separates PRISM from the Frama-C WP + CBMC route in the
  draft; the feedback never mentions it as an advantage nor as a cost (PRISM verifies the IR it can translate; what is
  outside the fragment is `UNENCODED`).
- **Stages the draft only half-credits.** `interval` (path-sensitive ranges; origin `lint`, never proves), `wp` (a small
  in-tree substitution prover, not Frama-C WP; ACSL it cannot encode is `ERROR`; `src/prism/stages/wp.cpp:1-40`),
  `contracts`, `bmc` (hand encoder, now the differential oracle), `pir` (the main prover), `conc` (threads, never
  proves, `docs/CONCURRENCY.md`), `harness`, `review`, `concolic`, `fuzz`, `rapid`, `muttest`, `ltl`.
  The draft's "NEEDS-HARNESS for 20 of the 29 WP-proved functions" mixes the in-tree `wp` stage with `pir`; the
  `wp` stage is not Frama-C (`docs/PLAN.md` stage 5b calls it "in-tree Frama-C WP", but the code is a substitution prover).
- **Caches.** Solver query cache (SHA-256 of normalised formula), certificate store with LRU cap, lowered-library-model
  cache, learned-scheduler history `solve_times.json`, proof store (`PRISM_PROOF_CACHE`).
- **Parallelism and budgets.** `--jobs`, per-query solver members, `PRISM_FUNCTION_BUDGET`, `PRISM_HOUDINI_BUDGET`,
  `PRISM_CERTIFY_BUDGET`, memory budget with Z3 interruption, killable child processes, solver watchdog.
- **Known unsoundness list.** `docs/CONFORMANCE.md` lists constructs where the engine is known to prove something false;
  the User Guide says to treat proofs of code that uses them with care (`docs/USER_GUIDE.md:257-262`). A report that
  presents PRISM to buyers should not call a `PROVED` unconditional.
- **Windows/LP64 front end, C++ models, SV-COMP mode** (`docs/PIR.md:48-60`, `docs/SVCOMP.md`).

4. Item 2: proposing two named proof verdicts; the lattice is Lean-proved (item 2).

    scheduler trained on them predicts those tools, not PRISM stages (item 11).
